# Version 0.2 verification — October 1, 2026

Built on this Apple Silicon Mac with GNU Fortran 16.2.0, FFTW 3.3.11, Hamlib 4.7.2, CMake 4.4.3 and installed Swift/Xcode tools.

- Four upstream core tests and 17 Python tests passed: WAV interoperability/validation, live message assembly, rolling receive buffer, Hamlib dummy CAT/PTT, tuning guards and independent timed release.
- Native audio harness passed a simulated 48 kHz stereo capture through channel selection, sample-rate conversion and JTTY decoding.
- Built-in MacBook speaker silent playback drained successfully. No radio output device was selected for this test.
- Native station harness passed queued transmissions, frequency/mode control, release, Tune cancellation, PTT test and shutdown against Hamlib's dummy radio. It used near-zero output on built-in speakers, no radio and no microphone.
- Prior WAV interface was visually verified. New Conversation controls were inspected through the native accessibility tree; subsequent setup-page UI inspection was blocked by the computer-use tool's native pipe failure.
- Upstream checkout remains unmodified.

No FT-710 serial or USB audio device was visible. Actual hardware CAT/PTT, microphone/USB capture permission flow, RF levels, weak-signal characterization and over-the-air interoperability remain unverified. A dummy backend is not evidence of actual radio behavior.

The app is a local developer bundle requiring its build-folder location and external Homebrew libraries. Packaging, notarization and installation on another Mac remain future work. A process-local PTT watchdog cannot cover forced termination or a disconnected cable.

The upstream protocol is unchanged. Complete marks receipt of an end marker, not a guarantee against false decodes. Future upstream protocol changes may require updating the pinned source.

Receive troubleshooting update: fixed an input callback race that attempted to enqueue during AudioQueueStop/Dispose (-66632). All 21 existing automated tests and native conversion passed afterward. A connected USB Audio Device (one input, two outputs, 48 kHz) was detected, but a receive-only start/stop hardware test failed at Start input (-66681); CoreAudio logged server start failures and a timeout. Real receive capture therefore remains unverified. No output or PTT was used in this test.

PortAudio receive fix: AudioQueue and an AUHAL probe failed while an independent PortAudio probe opened the exact same USB Audio Device (CoreAudio ID 125) at 48 kHz and captured nonzero samples (peak 0.118). The app now uses PortAudio for receive capture through `native/capture.c`, verifies the selected CoreAudio device ID before starting, and retains the existing Swift channel selection and 12 kHz conversion. The integrated harness passed three capture/stop/restart cycles, receiving 96 converted batches with peak 0.097. All four upstream tests, 17 Python tests and native conversion checks passed after this change. These receive-only checks used no audio output or CAT/PTT. Earlier USB capture limitations above describe the superseded AudioQueue implementation. RF transmission and two-station interoperability remain unverified.

Runtime routing investigation: GUI process logs confirmed AUHAL selected USB device 125 then switched to built-in microphone 118 roughly two seconds later. Initial stream-ID validation therefore did not establish sustained routing. Added macOS 14.2+ process-input-device checks every 250 ms that stop capture on an unexpected device. The receive harness now holds each capture for three seconds; three USB restart cycles passed with 840 converted batches and nonzero signal. The GUI-specific switch cause remains unresolved; Standard Mic Mode is the next user-side comparison. All 21 automated tests and native conversion passed.

Later comparison reproduced runtime microphone redirection in the USB harness both with dummy CAT and without any CAT connection. This does not isolate Hamlib as the cause; radio serial hardware is not required. The route guard stopped each capture and the hardware tests correctly failed. Earlier passing capture runs do not establish that the redirection is resolved. Added optional --dummy-cat comparison and unbuffered diagnostic output to the harness.

Direct-device capture update: Standard Mic Mode confirmed by user, ruling out the previous voice-isolation hypothesis. Replaced PortAudio/AUHAL receive with AudioDeviceCreateIOProcID on the selected CoreAudio device ID. Callback checks the supplied device identity and copies native Float32 input; any supplied output buffers are zeroed, with no modulation or PTT. Three USB capture/restart cycles with dummy CAT passed: 811 converted batches, peak 0.111, no route errors. All 21 automated tests and native conversion passed. GUI validation is still pending; prior failed PortAudio route tests remain historical evidence. PortAudio dependency removed.

Low-level investigation: latest USB checks received callbacks but returned exactly zero samples through both direct capture and the independent PortAudio probe. Test application input-muted state was false. Added explicit input-stream enable/output-stream disable to the capture IOProc, an app-muted check, and a 1024-sample rolling waterfall FFT window (previously short individual callback blocks were zero-padded). Automated tests and native conversion passed; hardware callback/restart worked but nonzero reception was not verified in this run. No gain change can restore exact zero samples.

WSJT-X architecture review: see WSJTX-AUDIO-CAT-REVIEW.md. CAT serial DTR/RTS now forced OFF, following the explicit serial control supported upstream. FT-710 config acceptance verified without opening a port. New real-LiveStation regression with continuous synthetic input and actual Hamlib dummy CAT passed connection, polling, frequency/mode changes and shutdown. No hardware or audio device used. Hardware removed by user; this correction cannot yet be called a verified hardware fix.

Version 0.3 replaces the custom receive backend with the actual upstream WSJT-X Qt SoundInput and AudioDevice code, built unchanged from the pinned checkout in a threaded helper. Five CTests, 17 Python tests and three Swift harness checks passed (PCM transport, conversion, CAT/receive lifecycle). Qt device enumeration works and confirmed no USB radio is attached. Hardware capture, sustained GUI input and transmit interoperability remain unverified. See WSJTX-AUDIO-CAT-REVIEW.md for the implementation and limits. Earlier custom-backend hardware results do not validate this replacement.
